# Ballerz contribution and testing policy

**Every implemented behaviour requires executable tests at each logical layer that enforces it and at the boundaries it crosses.** This applies to game simulation, rules, clients, storage, workers, permissions, agents, economic calculations, Solana instructions and release operations. A feature is complete when the team can reproduce its intended result, its rejection cases and its recovery behaviour. Existing functionality with missing evidence is a tracked coverage gap. New behaviour and fixes ship with their tests in the same change.

## Before implementation

Link the feature to its [backlog ID](docs/studio/backlog.md) and source decision. Identify who acts, who has authority, the prior state, the expected observable result and what must remain true after failure. Write acceptance examples using actual units, clocks and identifiers. For an economic rule, name the payer, payee, asset, custodian, enforceable restriction and finality requirement. For a balancing experiment, record the control, seed, rule version, target and what result would cause us to change the parameter.

## Evidence required

| Layer | Use it to prove | Examples |
| --- | --- | --- |
| Unit and property tests | Exact boundary behaviour and invariants across generated input sequences | Before/at/after a deadline, partial weeks, rounding, caps surviving transfer, budgets conserving BB, published draw reproduced from seed. Save failing seeds. |
| Service, database and worker integration | Real commands update durable state once and enforce permissions | Two submissions race, server restarts, old database records load, migration can resume, a stale manager cannot approve a sale. Exercise normal API entry points. |
| Solana runtime | Signed instructions execute with expected account and token transitions | Use LiteSVM for fresh state, rights, mint/recipient bindings, account ownership, token conservation, insufficient funds, atomic rollback, expiry, replay and stale approvals. Run the instructions built by the application. |
| Local validator and RPC | Client, signer, transaction history, confirmation, indexer and job recovery agree | Use an ephemeral local validator, a real client and disposable keys. Test lost RPC replies, delayed indexing, mismatched networks, separately signed submissions, concurrent workers and restart after finalization. |
| Client and end-to-end | A person can complete the journey and see the correct authority, cost and state | Browser tests exercise signup, lineup, pending/rejected/finalized payments, transferred ownership, keyboard use and private/public views. Human playtests assess clarity, tactical agency and accessibility. |
| Simulation and balance | A tuning rule creates the intended footballing and economic outcomes | Match paired winger/keeper histories, simulate mass retirement, no-sponsor economies and multi-season cohorts. Keep seed sets, distributions, configuration and exceptions with the build. |
| Devnet and operational rehearsals | A release candidate can operate and recover on the intended cluster | Use dedicated test assets and capped funding. Save cluster, build, programme/mint IDs, fixture ID, signatures and balances. Rehearse reconciliation, key rotation, restore and pausing payouts. |

Pure game rules need direct and integration evidence wherever their outputs are consumed. Chain-backed functionality requires real instruction execution and a validator/RPC integration path. A signed receipt establishes what transferred. Matchday tests must independently establish who qualified. Check the BB token delta separately from SOL fees and rent. A successful signature, a screenshot, a stubbed RPC response or a line-coverage percentage alone cannot demonstrate that the right club received the right amount.

## Merge, release and incident gates

1. **Every pull request.** Run the existing deterministic `node:test` suite in `matchday` and the tests for the affected logical parts. Include fast signed-transaction tests for instruction changes, a real local-validator path for settlement/client changes, and browser journeys for affected user flows. A changed invariant requires a failing-before regression or an equivalent reproducible test. Review permissions, migrations, prior records and concurrent operations.
2. **CI and evidence.** Give each required workflow a stable check name; configure protected-branch checks after validating them. Fail if a required suite silently skips, cannot set up its environment or asserts no relevant cases. A red test keeps its issue open. A flaky test gets an owner and reproducible evidence; rerun alone does not clear an unresolved release risk. Keep wallets and secrets out of artifacts. Store only public test identifiers and redacted logs.
3. **Release candidate.** Run the full regression suite on the candidate commit, perform the first-time and returning-user journeys, run balance/scale tests against the changed release, exercise migration and recovery from a prior release, and record a Devnet check for changed chain behaviour. Log versions, expected/actual results, coverage gaps and the producer/QA decision. Failed funds, custody, data integrity or permission checks block release.
4. **After release.** Reconcile BB, signers, receipts, indexes and club ledgers. A duplicate payment, wrong owner, hidden data disclosure or irrecoverable fixture is a release-blocking incident. Pause the affected operation, preserve evidence, reconcile before retrying, and add a regression test before closing the incident. A code rollback cannot reverse a finalized transfer.

## Reference acceptance case

Start with 16,000 test BB in a dedicated vault and zero in both club accounts. Two managers submit valid sheets and play an eligible fixture. Assert the server's readiness decision, the signed mint and destinations, final vault balance zero, each club balance 8,000 and exactly one receipt for that fixture. Retry with a fresh blockhash. Restart after finalization and before the SQLite receipt write. Recover the same signature both times. In a new world give the vault only 8,000 and verify neither club is paid and no receipt is created. Then settle a second legitimate fixture after funding and verify both clubs can earn again.

**Current evidence.** Run `node --test` from `matchday` after installing its locked dependencies. The matchday suite and Devnet demonstration exist.
